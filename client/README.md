# ClipX Client - Desktop App

Rust desktop application for clipboard sync. Connects to the C# clipboard bridge, stores history locally, syncs with a remote server, and also acts as a LAN peer for direct device-to-device sync without the server.

## Responsibilities

- Receive clipboard events from the C# core bridge via named pipe IPC
- Store clip history in local SQLite
- Sync clips to the cloud server via REST + WebSocket
- Run an embedded HTTP/WebSocket server for direct LAN peer sync
- Provide a tabbed GUI (History, Devices, LAN Peers, Log) and an overlay picker
- System tray integration and customizable global hotkeys
- Offline queue with exponential backoff
- Apply inbound clips to the OS clipboard via the bridge (auto-paste)

## Build and Run

```powershell
cargo build --release -p clipx-client
cargo run -p clipx-client
```

Data lives in the platform app-data directory (`%APPDATA%\clipx\ClipX\` on Windows). The SQLite database `clipx.db` holds clips, queue, settings, and trusted LAN peers.

## Configuration

Settings are stored as a JSON blob in the `settings` table under the `config` key. Defaults:

```json
{
  "server_url": "https://localhost:8443",
  "device_id": "<auto-generated UUID>",
  "device_name": "<hostname>",
  "user_id": "<auto-generated UUID>",
  "jwt": null,
  "overlay_hotkey": "Ctrl+Shift+V",
  "e2e_enabled": false,
  "local_sync_port": 41234,
  "lan_enabled": true,
  "auto_paste_inbound": true,
  "public_key": "<auto-generated on first run>",
  "private_key": "<auto-generated on first run>"
}
```

Override at first launch via env vars: `CLIPX_JWT`, `CLIPX_USER_ID`, `CLIPX_DEVICE_ID`.

## Modules

| Module | Purpose |
|--------|---------|
| `ipc` | Named pipe client to the C# core bridge (inbound events, `set_clipboard` RPC) |
| `storage` | SQLite persistence for clips, queue, settings, trusted LAN peers |
| `sync` | Cloud REST upload, cloud WebSocket listener, retry queue, embedded LAN HTTP/WS server |
| `lan_sync` | Outbound LAN peer WebSocket manager (connects to each paired peer) |
| `crypto` | Keypair generation, encryption primitives (E2E roadmap) |
| `hotkeys` | Global hotkey registration |
| `tray` | System tray icon and menu |
| `overlay` | Hotkey-driven clip picker with paste injection |
| `ui` | Main eframe GUI (History, Devices, LAN Peers, Log, Settings) |
| `state` | Shared in-memory state between background tasks and the UI thread |

## LAN Peer Sync

The client runs an embedded Axum server on `local_sync_port` (default 41234) with three routes:

- `POST /pair/request` — incoming pairing handshake; surfaces a modal in the receiver's UI
- `POST /pair/accept` — handshake completion callback
- `GET /ws?token=<session_token>` — WebSocket stream of clips between paired peers

Discovery is **manual IP entry**. In the LAN Peers tab, enter the other device's address (`192.168.0.10` or `192.168.0.10:41234`) and click **Request Pair**. The other side gets an accept modal. After acceptance, both sides store the peer (including a shared `session_token`) in their local SQLite, and the outbound WebSocket connection comes up automatically.

Once a peer is paired, clips captured locally are broadcast to every connected peer's WebSocket; inbound clips are stored and, if `auto_paste_inbound` is true, written to the OS clipboard via the bridge.

LAN sync does not require the cloud server to be reachable.

## Cloud Sync

When configured with a `server_url` and `jwt`, the client:

- `POST`s each captured clip to `/api/v1/clips`
- Maintains a WebSocket to `/api/v1/ws?token=<jwt>` for inbound clips from other devices on the same user account
- Falls back to a persistent retry queue when the server is unreachable, with exponential backoff and a configurable retry limit

LAN and cloud paths operate independently — a clip captured locally goes to both.

## Hotkeys

Default overlay hotkey: `Ctrl+Shift+V`. Supported modifiers: `Ctrl`, `Shift`, `Alt`, `Super`/`Win`. Supported keys: `A-Z`, `0-9`, `F1-F12`, `Space`, `Tab`, `Escape`.

## Status Bar

The top status bar shows three live indicators:

- **Bridge** — green when the named pipe to the C# core is connected, red otherwise
- **Cloud** — green when the WebSocket to the cloud server is up
- **LAN** — green when at least one paired LAN peer is connected

If the bridge is disconnected, auto-paste on inbound clips will fail with a `Auto-paste skipped — bridge unreachable` warning in the Log tab.
