# Offline LAN Sync — Functional + Technical Spec

This document describes the **device-to-device LAN sync** subsystem: how two ClipX clients on the same network pair without the cloud server, and how they exchange clips directly afterwards.

> **Scope note**: the cloud server (REST + WebSocket + Redis relay) remains the canonical sync path for cross-network and asynchronous delivery. LAN sync is an additive, server-independent path that works offline.

---

## Pairing Flow

1. **Discovery** — *manual IP entry*.
   The LAN Peers tab in the GUI accepts an IP or `ip:port` (default port `41234`) and a "Request Pair" button. There is no automatic discovery in the current build — see the *Discovery* note at the bottom for the history and rationale.

2. **Request**
   Device A sends `POST http://<B>/pair/request` with its identity payload:
   ```json
   {
     "from_device_id": "<UUID>",
     "from_name": "Laptop A",
     "from_public_key": "<base64>",
     "ip": "192.168.0.10",
     "port": 41234,
     "session_token": "<32-byte hex>"
   }
   ```
   B responds `202 Accepted` (request queued for user decision) or `409 Conflict` (already paired).

3. **User decision on B**
   B's GUI shows a modal: *"Laptop A wants to sync"* with the peer's IP and device ID. User clicks Accept or Reject.

4. **Acceptance**
   On Accept, B stores A as a trusted peer (using the `session_token` A proposed) and calls back to A:
   ```
   POST http://<A>/pair/accept
   {
     "accepted": true,
     "to_device_id": "<UUID>",
     "to_name": "Laptop B",
     "to_public_key": "<base64>",
     "ip": "192.168.0.20",
     "port": 41234,
     "session_token": "<same token>"
   }
   ```
   A persists B as a trusted peer with the same `session_token`. Both sides now have a row in `peer_devices` referencing the other, sharing one bearer token.

5. **Automatic sync**
   The `LanPeerManager` background task notices the new row and opens an outbound WebSocket to `ws://<peer.ip>:<peer.port>/ws?token=<session_token>`. The server-side `/ws` handler validates the token against its own `peer_devices` table; if valid, it upgrades. From this point clips flow in both directions.

## Sync Protocol

Once a peer's WebSocket is open, every locally captured clip is broadcast as a text message:

```json
{
  "type": "clip",
  "payload": {
    "id": "<UUID>",
    "user_id": "<UUID>",
    "device_id": "<UUID>",
    "content": "Hello world",
    "format": "text",
    "e2e": false,
    "created_at": "2026-06-05T12:34:56Z"
  }
}
```

On receipt the peer:
- inserts the clip into local SQLite (deduplicated by `id`)
- pushes it into the UI history
- if `auto_paste_inbound` is enabled, sends `set_clipboard` over the named pipe to the C# core bridge so the clip appears in the OS clipboard

## Security

- **Authentication**: shared `session_token` (random 32 bytes, hex-encoded) generated by the requester and confirmed by the acceptor. Any future connection to `/ws` without the matching token returns `403`.
- **Transport**: HTTP/WebSocket (no TLS in current build). Acceptable on a trusted LAN; a TLS upgrade with self-signed pinned certificates is planned.
- **Authorization**: every peer connection is gated by the `peer_devices` table on the receiving side; "Forget" in the GUI removes the row and immediately invalidates the peer's token.
- **E2E encryption**: clips have an `e2e` boolean; key exchange and per-clip AES-GCM are wired into the data model but not yet enabled.

---

## Data Model (client SQLite)

`peer_devices`
- `id TEXT PRIMARY KEY` (peer's `device_id`)
- `name TEXT`
- `public_key TEXT`
- `ip TEXT`
- `port INTEGER`
- `session_token TEXT`
- `paired_at TEXT` (RFC3339)

`peer.online` is derived at runtime from WebSocket connection state, not persisted.

## GUI

- **LAN Peers tab**
  - **Pair by IP** — text field + "Request Pair" button; status/errors land in the Log tab.
  - **Paired LAN Devices** — list with online/offline dot and a "Forget" button per row.
- **Pairing request modal** — shown on the receiver when an inbound `/pair/request` arrives; displays peer name, IP:port, and device ID; Accept / Reject buttons.
- **Status bar** — "LAN" indicator: gray (server off), blue (no peers connected), green with count (≥1 peer online).

## Endpoints (embedded server on each client)

| Method | Path | Purpose |
|---|---|---|
| POST | `/pair/request` | Inbound pair request → surfaces accept modal |
| POST | `/pair/accept` | Callback from acceptor after user clicks Accept |
| GET  | `/ws?token=<session_token>` | WebSocket clip stream for paired peers |

Listen port is `local_sync_port` (default `41234`).

## Discovery — historical note

An mDNS-based auto-discovery layer existed in earlier revisions (service type `_clipboardsync._tcp.local.`, advertising `device_id`, `name`, port, and pubkey fingerprint). It was removed because UDP 5353 on Windows is heavily contended by Bonjour, Chrome/Edge (Cast), Microsoft Copilot, and NVIDIA's GameStream — leading to silent bind failures and announcements going out the wrong interface in multi-NIC setups (e.g. with Hyper-V's vSwitch). Manual IP pairing proved more reliable and is sufficient for current testing.

If auto-discovery returns, the recommended path is a **custom UDP broadcast on a non-standard port** (sidestepping the 5353 squatter problem), or **cloud-mediated discovery** (the server already knows which devices belong to the user and could return their LAN IPs).

## Firewall

Each device must allow inbound TCP on `local_sync_port` (default `41234`) through Windows Firewall, scoped to the `clipx-client.exe` binary on the Private profile. See `firewall.txt` at the repo root for ready-to-run PowerShell.
